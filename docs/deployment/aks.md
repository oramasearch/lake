# `Lake/prod` on AKS

The production lake instance runs on the sandbox AKS cluster `orama-production-cluster-01`,
deployed by `oramasearch/orama-operator` from one `Lake` resource. This page is the current
state and the runbook; the CR's field reference is the operator's `docs/crd-reference.md`.

## What exists (2026-09-02)

| lake pods | Deployment `lake-prod`, **3 replicas**, image `oramasearch/lake:20260902c` (the control surface + UI), args `--listen 0.0.0.0:4900 --node prod`, readiness `GET /`; env `LAKE_ADMIN_TOKEN`, `LAKE_CONTROL_DB_URI`, `LAKE_CONTROL_DB_PASSWORD` |

## Audit identity deployment

The audit stream signs every event with lake's own TAAP/1 Ed25519 identity. The deployment
provides `LAKE_IDENTITY_SEED` as a base64 32-byte Secret value when an operator-managed identity
is available. Lake uses that Secret directly and does not copy it into the control database. When
it is absent, lake generates a seed at first start and stores it only as AES-256-GCM ciphertext in
the control database. `LAKE_INSTANCE_KEK` is the customer-independent key-encryption key for that
ciphertext and must be supplied as a separate Secret value; it never appears in an API response,
audit event, pod argument, or log line.

`rotate_identity` creates a generated successor identity, so retain `LAKE_INSTANCE_KEK` even when
`LAKE_IDENTITY_SEED` supplies the current identity.

The audit and lifecycle migrations (`0005_audit` and `0006_repository_lifecycle`) are subject to
the Phase 6 operator waiver: lake carries the source schema now, while the operator's vendored
schema, guard table, and Secret projection land once per completed wave in a separate operator
pull request. Until that PR is deployed, do not enable these features on an existing production
Lake with a schema guard older than `repository_refs`.

## Repository store volume

Lake opens one libliquid store for each customer at
`LAKE_STORE_ROOT/<customer id>/store`. The operator supplies `LAKE_STORE_ROOT` as a writable
PersistentVolume mount; Lake neither creates nor selects it. The required operator work is issue
#132 and the companion schema and guard update is pull request #134. liquid #160's sync contract
and client API are pinned; push and pull endpoints await libliquid's public repository/store
binding and codec required for lake's customer-store server.

## Runbook

**Roll a new lake image.** Release an immutable CI-built image (see
[`../build/container-image.md`](../build/container-image.md)) by creating and pushing a
Docker-compatible Git tag:

```sh
git tag <tag>
git push origin <tag>
```

Wait for the GitHub Actions `image` workflow to publish `oramasearch/lake:<tag>`, then change
`spec.image` on the Lake and apply; the Deployment rolls. Never deploy `latest` or an image pushed
from a workstation. The workflow credentials and the manual retry path are documented in
[`../build/ci.md`](../build/ci.md).

**Roll the operator.** From the operator repo on the branch to deploy:

```sh
docker buildx build --platform linux/amd64 -t oramasearch/orama-operator:lake-crd-<sha> --load .
docker push oramasearch/orama-operator:lake-crd-<sha>
kubectl apply -f config/crd/bases/orama.cloud_lakes.yaml          # helm never upgrades crds/
helm upgrade orama-cloud-v1-operator ./chart -n orama-system \
  --set operator.image.repository=oramasearch/orama-operator \
  --set operator.image.tag=lake-crd-<sha> \
  --set 'operator.imagePullSecrets[0].name=oramasearch-dockerhub'
kubectl rollout status deploy/orama-cloud-v1-operator -n orama-system
```

Immutable tags, never `v1-sandbox` with `IfNotPresent`: the operator docs record the stale-cache
failure that motivates this.

**Create a Lake.** Namespace and the two Secrets first, then the Lake:

```sh
kubectl create namespace <ns>
for s in oramasearch-dockerhub cloudflare-api-token; do
  kubectl get secret $s -n orama-system -o json \
    | python3 -c 'import json,sys; s=json.load(sys.stdin); s["metadata"]={"name":s["metadata"]["name"],"namespace":"<ns>"}; print(json.dumps(s))' \
    | kubectl apply -f -
done
kubectl apply -f lake.yaml
kubectl wait lake/<name> --for=jsonpath='{.status.schemaPhase}'=Applied --timeout=600s
```

**Verify.** `kubectl get lake <name>` → READY = replicas, DB `1/1`, SCHEMA `Applied`, PHASE
`Ready`; `curl https://<host>/v1/server_info` reports `"store": "postgres"`; with
`T=$(kubectl get secret lake-<name>-admin -n <ns> -o jsonpath='{.data.token}' | base64 -d)`:
`curl -H "Authorization: Bearer $T" https://<host>/v1/list_repositories`, and the sign-in form at
`/login` with the same token opens `/repositories`. The manager logs filtered on
`"controller": "lake"` show reconcile errors.

After the audit migration and identity Secrets are present, verify the identity and chain:

```sh
curl https://<host>/v1/identity
curl -H "Authorization: Bearer $T" https://<host>/v1/verify_audit
```

**Delete.** `kubectl delete lake <name>` removes everything it owns, including the CNPG cluster
and **its data**; the namespace is not owned and stays.

## Not production-grade yet

- One Postgres instance, no backups (operator issue #122 for hardening; CNPG backup config is a
  `spec.postgres` addition).
- No resource limits, liveness probe or PodDisruptionBudget on the lake pods.
- TLS terminates at Cloudflare only; the Ingress is port 80.
- Zetta data plane not provisioned (operator issue #125).
