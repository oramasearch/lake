# `Lake/prod` on AKS

This page contains the AKS runbook. The current production facts are in the dated
[2026-09-08 deployment record](production-2026-09-08.md), which supersedes the historical
inventory below. The production lake instance runs on the sandbox AKS cluster
`orama-production-cluster-01`, deployed by `oramasearch/orama-operator` from one `Lake` resource.
The CR field reference is the operator's `docs/crd-reference.md`.

## Audit identity deployment

The audit stream signs every event with lake's own TAAP/1 Ed25519 identity. The deployment
provides `LAKE_IDENTITY_SEED` as a base64 32-byte Secret value when an operator-managed identity
is available. Lake uses that Secret directly and does not copy it into the control database. When
it is absent, lake generates a seed at first start and stores it only as AES-256-GCM ciphertext in
the control database. `LAKE_INSTANCE_KEK` is the customer-independent key-encryption key for that
ciphertext and must be supplied as a separate Secret value; it never appears in an API response,
audit event, pod argument, or log line.

`rotate_identity` creates a generated successor identity, so retain `LAKE_INSTANCE_KEK` even when
`LAKE_IDENTITY_SEED` supplies the current identity.

The audit and lifecycle migrations (`0005_audit` and `0006_repository_lifecycle`) are subject to
the Phase 6 operator waiver: lake carries the source schema now, while the operator's vendored
schema, guard table, and Secret projection land once per completed wave in a separate operator
pull request. Until that PR is deployed, do not enable these features on an existing production
Lake with a schema guard older than `0006_repository_lifecycle` (its marker was the
`repository_refs` table, dropped by `0064`).

## Repository store volume

Lake opens one libliquid store for each customer at
`LAKE_STORE_ROOT/<customer id>/store`. The operator supplies `LAKE_STORE_ROOT` as a writable
PersistentVolume mount; Lake neither creates nor selects it. The required operator work is issue
#132 and the companion schema and guard update is pull request #134. The source tree pins liquid
#160 and #165 and implements push and pull over the customer store. Production requires a lake
image containing those endpoints and the operator volume work before they are enabled there.
One lake process owns the store root at a time. From lake#479 a second process waits for the owner
to drain and hands over without refusing a request, so a single-replica Lake on one store volume
can roll with the operator's `spec.rollout.overlapOnSharedStore` (a surge) instead of `Recreate`.
The image must contain lake#479 before the opt-in is turned on: an older image refuses to start
beside the running pod and the surge stalls. See
[`store-volume.md`](store-volume.md#the-hand-off).

## Secrets

Lake has two levels of secrets ([secrets.md](secrets.md)). Orama's own (the Stripe and OpenAI keys
below, the instance key, the admin token) are environment variables of the platform, set here
through `spec.env` and Kubernetes Secrets; never a secret mount. A user's workspace secret lives in
lake's secret store and reaches a Kubernetes Secret only as a projection the operator writes when an
app, service or deployment mounts it (lake#625, decision 58). [secrets.md](secrets.md) has the audit
of every Secret on this cluster that user apps, services and deployments use, and the projection
mechanism; it needs an operator with the lake-secret projection (orama-operator, branch
`lake-625-secret-projections`) and its updated `LakeApp` and `LakeSealedSecret` CRDs installed before
it rolls.

## Speech-to-text key

Speech-to-text (`transcribe`, and `create_transcript` from audio, lake#561,
[`../api/transcripts.md`](../api/transcripts.md)) and the model gateway (`/openai/v1/*`, every agent
model call, lake#248, [`../api/model-gateway.md`](../api/model-gateway.md)) need
`LAKE_OPENAI_API_KEY` in the lake pod. Without it they answer `not_supported` and the rest of lake is
unaffected. `LAKE_TRANSCRIBE_MODEL` is optional (default `gpt-4o-transcribe`), and so is
`LAKE_MODEL_PROVIDER_URL` (default `https://api.openai.com/v1`).

On the dev cluster the key already exists as Secret `lake-prod-openai`, key `OPENAI_API_KEY`, in
namespace `lake`, where the lake pods run. `spec.agents.openaiSecretName` used to name the same
Secret for the agents, which put the key into every agent pod; once the agents call their model
through the gateway it is removed, so only lake holds the key:

```sh
kubectl --context orama-production-cluster-01 patch lake prod --type json -p '[
  {"op": "remove", "path": "/spec/agents/openaiSecretName"}
]'
```

The operator then stops setting `OPENAI_API_KEY` in agent pods and stops copying the Secret into
workspace namespaces; copies it made before stay until deleted
(`kubectl get secret -A --field-selector metadata.name=lake-prod-openai`, every namespace but
`lake`). The Lake CRD's `spec.env` is a list of Kubernetes `EnvVar`s, so `valueFrom.secretKeyRef`
is supported. The operator appends each entry after its own variables and skips only the names it
manages (`lakeEnv` in the operator's `internal/controller/lake_controller.go`). The key never
enters the CR.

`spec.env` already holds `LAKE_LOG_MODE`, `LAKE_PUBLIC_HOST` and `LAKE_CLERK_PUBLISHABLE_KEY`, and a
merge patch would replace the whole list, so append with a JSON patch:

```sh
kubectl --context orama-production-cluster-01 patch lake prod --type json -p '[
  {"op": "add", "path": "/spec/env/-", "value": {"name": "LAKE_OPENAI_API_KEY",
   "valueFrom": {"secretKeyRef": {"name": "lake-prod-openai", "key": "OPENAI_API_KEY"}}}}
]'
```

The Deployment rolls. To check it, `transcribe` a short clip; the answer names its `model`. For the
gateway, ask Ask Orama something and read the turn's workspace usage: `usage_over_time` with
`dimensions: ["model_tokens"]` shows the tokens by agent `agent-ask-orama`.
Removing the entry turns speech-to-text off again. An image built before lake#561 ignores the
variable.

## Billing switch

Billing (lake#564, [`../api/billing.md`](../api/billing.md)) is on only where `LAKE_BILLING=on`.
Orama's own lake (lake.live, and `Lake/prod` on dev when billing is being exercised) sets it in
`spec.env`; an enterprise install leaves it unset, and lake then has no billing capability, page or
guide. `LAKE_BILLING_INSTRUCTIONS` (optional) is the payment text each invoice of the manual
provider shows. The schema must first carry `0073_billing` (guard `billing_guard`). Append with a
JSON patch, as for the speech-to-text key:

```sh
kubectl --context orama-production-cluster-01 patch lake prod --type json -p '[
  {"op": "add", "path": "/spec/env/-", "value": {"name": "LAKE_BILLING", "value": "on"}}]'
```

Removing the entry turns billing off at the next roll; the billing rows stay in PostgreSQL.

## Stripe

Stripe is lake's payment provider (decision 57, lake#620). Its keys are lake's own platform
credentials: on this cluster, the Secret `lake-prod-stripe` in namespace `lake`, referenced from
`Lake/prod`'s `spec.env` (`LAKE_STRIPE_SECRET_KEY` and `LAKE_STRIPE_WEBHOOK_SECRET` through
`valueFrom.secretKeyRef`, never a literal in the CR). Both values are **blank** today (2026-10-11),
so lake runs the manual provider.

**To set Stripe up, rotate a key or turn it off, follow the runbook:
[stripe.md](stripe.md).** On a Lake that does not yet carry the two `spec.env` entries, add them:

```sh
kubectl --context orama-production-cluster-01 patch lake prod -n lake --type json -p '[
  {"op": "add", "path": "/spec/env/-", "value": {"name": "LAKE_STRIPE_SECRET_KEY",
    "valueFrom": {"secretKeyRef": {"name": "lake-prod-stripe", "key": "secret_key"}}}},
  {"op": "add", "path": "/spec/env/-", "value": {"name": "LAKE_STRIPE_WEBHOOK_SECRET",
    "valueFrom": {"secretKeyRef": {"name": "lake-prod-stripe", "key": "webhook_secret"}}}}]'
```

## Runbook

**Roll a new lake image.** Release an immutable CI-built image (see
[`../build/container-image.md`](../build/container-image.md)) by creating and pushing a
Docker-compatible Git tag:

```sh
git tag <tag>
git push origin <tag>
```

Wait for the GitHub Actions `image` workflow to publish `oramasearch/lake:<tag>`, then change
`spec.image` on the Lake and apply; the Deployment rolls. Never deploy `latest` or an image pushed
from a workstation. The workflow credentials and the manual retry path are documented in
[`../build/ci.md`](../build/ci.md). Pages link the content-hashed stylesheet and font URLs, so a
Cloudflare cache purge is not part of a Lake rollout. The unhashed compatibility routes require
revalidation and cannot retain a prior deployment's bytes without checking Lake.

**Roll the operator.** From the operator repo on the branch to deploy:

```sh
docker buildx build --platform linux/amd64 -t oramasearch/orama-operator:lake-crd-<sha> --load .
docker push oramasearch/orama-operator:lake-crd-<sha>
kubectl apply -f config/crd/bases/orama.cloud_lakes.yaml          # helm never upgrades crds/
helm upgrade orama-cloud-v1-operator ./chart -n orama-system \
  --set operator.image.repository=oramasearch/orama-operator \
  --set operator.image.tag=lake-crd-<sha> \
  --set 'operator.imagePullSecrets[0].name=oramasearch-dockerhub'
kubectl rollout status deploy/orama-cloud-v1-operator -n orama-system
```

Immutable tags, never `v1-sandbox` with `IfNotPresent`: the operator docs record the stale-cache
failure that motivates this.

**Create a Lake.** Namespace and the two Secrets first, then the Lake:

```sh
kubectl create namespace <ns>
for s in oramasearch-dockerhub cloudflare-api-token; do
  kubectl get secret $s -n orama-system -o json \
    | python3 -c 'import json,sys; s=json.load(sys.stdin); s["metadata"]={"name":s["metadata"]["name"],"namespace":"<ns>"}; print(json.dumps(s))' \
    | kubectl apply -f -
done
kubectl apply -f lake.yaml
kubectl wait lake/<name> --for=jsonpath='{.status.schemaPhase}'=Applied --timeout=600s
```

**Verify.** `kubectl get lake <name>` → READY = replicas, DB `1/1`, SCHEMA `Applied`, PHASE
`Ready`; `curl https://<host>/v1/server_info` reports `"store": "postgres"`; with
`T=$(kubectl get secret lake-<name>-admin -n <ns> -o jsonpath='{.data.token}' | base64 -d)`:
`curl -H "Authorization: Bearer $T" https://<host>/v1/list_repositories`, and the sign-in form at
`/login` with the same token opens `/repositories`. The manager logs filtered on
`"controller": "lake"` show reconcile errors.

After the audit migration and identity Secrets are present, verify the identity and chain:

```sh
curl https://<host>/v1/identity
curl -H "Authorization: Bearer $T" https://<host>/v1/verify_audit
```

**Delete.** `kubectl delete lake <name>` removes everything it owns, including the CNPG cluster
and **its data**; the namespace is not owned and stays.

## Not production-grade yet

- One Postgres instance, no backups (operator issue #122 for hardening; CNPG backup config is a
  `spec.postgres` addition).
- No resource limits, liveness probe or PodDisruptionBudget on the lake pods.
- TLS terminates at Cloudflare only; the Ingress is port 80.
- Zetta data plane not provisioned (operator issue #125).
