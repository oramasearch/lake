# v0.1.0

**Released:** 2026-10-12 · **Branch:** `main` · **Previous:** none. This is the first tagged release.

Lake is where a customer designs, trains and ships AI on their own data. It is one C++26 binary
that serves a web app, a REST API and an MCP server over the same registry of capabilities. A
person signs in, gets workspaces, and in each one works with data, pipelines, models, agents,
apps, repositories and drives. Each workspace's data lives in that workspace's own Zetta;
Lake's Postgres holds only who the customers are and which Zetta serves which workspace.

Because this is the first release, **this page lists everything in it**: every feature by
area, every capability by name, every page of the web app and every guide. The capability
names were checked against the OpenAPI of the running deployment, so none is missing and none
is listed that the deployment does not serve.

## 1. One registry, three surfaces

Every capability is registered once and answered three ways: REST at `/v1/<capability>` (a
read is a `GET`, an action a `POST`), MCP at `/mcp` (each capability is a tool), and the web
app, which calls only `/v1`.

- **OpenAPI 3.1** at `/v1/openapi.json`, generated from the registry.
- **Workspace-scoped addresses**: `/w/<workspace_id>/v1/<capability>`,
  `/w/<workspace_id>/v1/openapi.json` and `/w/<workspace_id>/mcp`. The path supplies
  `workspace_id`, and an explicit value must match it.
- **One error table** ([`docs/api/errors.md`](../api/errors.md)): every error code with its
  REST status, and `401 unauthenticated` saying whether the credential was `missing`,
  `invalid` or `expired`.
- **One name per concept** ([`docs/api/naming.md`](../api/naming.md)), with the deprecated
  aliases still accepted.
- **For agents**: `/llms.txt`, `/llms-full.txt` and `/skills/lake/SKILL.md`.

Capabilities: `server_info` (no credential needed), `viewer`, `my_permissions`, `list_docs`,
`get_doc`, `mcp_setup`.

- **Teams** inside an organization.
- **Deleting an organization**, refused while it still owns a workspace.

## 4. Access, policy and audit

- **Grants** on objects, to people, teams and organizations, and **effective access**: who can
  reach an object and through which grant.
- **An audit trail split by subject.** Control-plane and identity events are in the central
  signed chain; events about a workspace's data are in that workspace. A person can read their
  own activity; an operator can read, export and verify the whole log and set its retention.
- **The instance identity**, which can be rotated.

Capabilities:

- Policy: `create_object`, `get_object`, `list_objects`, `create_grant`, `list_grants`,
  `revoke_grant`, `effective_access`, `entity_effective_access`.
- Audit: `audit`, `my_audit`, `export_audit`, `verify_audit`, `set_audit_retention`.
- Instance identity: `identity`, `rotate_identity`.

## 5. Workspaces

- **Many workspaces per account, each with its own Zetta**, started and sized through the
  operator. A workspace has an environment, a phase and a storage size that can grow.
- **Workspace data lives in the workspace's Zetta** as sealed records: Ask Orama
  conversations, opportunities, drives and share links, forge records, secrets and leases,
  application users, keys, settings and webhooks, agent task content, repository usage and
  the workspace's own audit. Migration `0070_drop_moved_tables` dropped the central copies.
- **The workspace's engine by name.** Every engine read and action is served at its own
  `/v1/<name>` and as an MCP tool, and `workspace_query`, `workspace_act` and `workspace_sql`
  reach the engine directly.
- **A workspace's own encrypted liquid store** in its Zetta: `move_workspace_store` plans,
  copies, verifies and switches one workspace's repositories into it, with the workspace's
  search index beside it.
- **Volume snapshots** of Lake's store volume or of a workspace's Zetta volumes, on request
  or on a schedule, for an operator or instance administrator.
- **Operator tools for the move into workspace Zettas**: `copy_workspace_records` plans,
  copies and verifies a retired control-store table, and `remove_space_store` removes an
  account's old store once every workspace is switched.
- **Deleting a workspace** lists what goes first (`dry_run`) and asks for the typed name.

Capabilities: `create_workspace`, `get_workspace`, `list_workspaces`, `update_workspace`,
`start_workspace`, `delete_workspace`, `workspace_status`, `set_workspace_storage`,
`workspace_engine_info`, `workspace_openapi`, `workspace_query`, `workspace_act`,
`workspace_sql`, `copy_workspace_records`, `move_workspace_store`, `remove_space_store`,
`request_volume_snapshot`, `volume_snapshots`.

## 6. Ask Orama

Ask Orama is the home page for a signed-in person: a conversation that answers from the
workspace, proposes work, and acts only after the person confirms a proposal. The same
conversation is in the side panel on every page. Conversations are kept in the workspace's
Zetta and can be deleted.

Capabilities: `send_ask_message`, `settle_ask_turn`, `confirm_ask_proposal`,
`get_ask_conversation`, `delete_ask_conversation`.

## 13. Secrets, encryption keys and certificates

### Secrets

- **Secret mounts** owned by an organization or a workspace, kept sealed in the workspace's
  Zetta.
- **Versioned secrets**: put, read, metadata, soft delete, undelete and destroy.
- **Dynamic secrets** with leases that are renewed and revoked.
- **A sealed projection for Kubernetes**: a user's secret reaches a Kubernetes Secret only
  as a sealed copy minted for the operator.

Capabilities: `create_secret_mount`, `get_secret_mount`, `list_secret_mounts`,
`delete_secret_mount`, `put_secret`, `read_secret`, `list_secrets`, `secret_metadata`,
`delete_secret_versions`, `undelete_secret_versions`, `destroy_secret_versions`,
`lease_dynamic_secret`, `renew_dynamic_secret`, `revoke_dynamic_secret`,
`mint_sealed_secret`.

### Encryption keys

Keys that never leave Lake: encrypt and decrypt, sign and verify, HMAC, derive a key, rewrap
to a newer version, rotate a key, and rotate a customer's key-encryption key.

Capabilities: `create_encryption_key`, `get_encryption_key`, `list_encryption_keys`,
`rotate_encryption_key`, `encrypt`, `decrypt`, `rewrap`, `sign`, `verify`, `hmac`,
`derive_encryption_key`, `rotate_customer_kek`.

### Certificates

A private root and online intermediate per customer: client, device and agent certificates, SSH user and
host certificates, and SPIFFE X.509 and JWT SVIDs. An agent's certificate can be checked,
rotated and revoked. ACME is served at `/acme/*`.

Capabilities: `create_pki_authority`, `issue_client_certificate`,
`issue_device_certificate`, `issue_agent_certificate`, `check_agent_certificate`,
`rotate_agent_certificate`, `revoke_agent_certificate`, `issue_ssh_user_certificate`,
`issue_ssh_host_certificate`, `issue_x509_svid`, `issue_jwt_svid`.

## 14. Recovery

- **Account recovery** by email, by a recovery code, or by an administrator's approval, with
  recovery contacts and notifications.
- **Repository key recovery**, with its status.
- **Root recovery** (break glass) for the instance.

Capabilities: `configure_recovery_contact`, `begin_email_recovery`, `recover_with_code`,
`begin_admin_recovery`, `approve_admin_recovery`, `complete_recovery`,
`claim_recovery_deliveries`, `list_recovery_notifications`, `recover_repository_key`,
`repository_recovery_status`, `begin_root_recovery`, `complete_root_recovery`.

## 15. Transparency and replication

- **A transparency log**: entries appended, checkpoints published, inclusion and consistency
  proofs, tiles, proof bundles, and a public scan of everything logged for one identity.
- **TUF metadata**: initialized, published, and its root rotated.
- **Trusted timestamps**: a checkpoint timestamped by an outside authority, and the evidence
  renewed before it ages out.
- **Replication** of the log to another Lake.

Capabilities: `transparency_log_configuration`, `append_transparency_entries`,
`publish_transparency_checkpoint`, `transparency_checkpoint`,
`transparency_inclusion_proof`, `transparency_consistency_proof`, `transparency_tile`,
`transparency_proof_bundle`, `transparency_identity_scan`, `initialize_tuf`,
`publish_tuf_metadata`, `tuf_metadata`, `rotate_tuf_root`, `timestamp_checkpoint`,
`timestamp_evidence`, `renew_timestamp_evidence`, `replicate_transparency_log`,
`export_transparency_replication_batch`.

## 16. Usage and billing

### Usage

- **Usage over time** per workspace: API and MCP calls, each model's answers, compute as CPU,
  RAM, GPU and GPU memory, and storage, against the period before, with CSV.
- **Limits** per dimension, and a storage quota.
- **Repository usage by hour**: transfer and build time.
- **An operator's view** across every account.

Capabilities: `usage_over_time`, `usage_limits`, `set_usage_limit`, `metering_usage`,
`set_storage_quota`.

### Billing

Billing is off unless `LAKE_BILLING` is set, so an enterprise install does not bill; usage
tracking is on everywhere.

- **A price list**: one rate per usage dimension, published from a month.
- **This month's bill so far**: usage times rate.
- **Invoices**: issued by the operator, read and printed, paid or voided.
- **Stripe** as the payment provider, or a manual provider with payment instructions.

Capabilities: `price_list`, `set_price_list`, `billing_account`, `bill_preview`,
`issue_invoice`, `list_invoices`, `get_invoice`, `record_invoice_payment`, `void_invoice`.

## 19. Serving, protocols and operations

- **One binary**, `lake`, listening on port 4900 by default, with an in-memory control plane
  for demos (`--memory-store`) or Postgres (`--control-db`).
- **Protocol routes** beside the API: liquid sync, the OCI registry (`/v2/*`), npm, Python
  and debuginfod paths, a Hugging Face subset (`/api/models/*`), SCIM (`/scim/v2/*`) and ACME
  (`/acme/*`).
- **Probes and metrics**: `/healthz`, `/readyz`, and Prometheus metrics at `/metrics`.
  Request logs carry route patterns, never raw paths.
- **Bounded serving**: limits on connections, long requests per caller, header, idle and
  transfer timeouts, and per-route body sizes.
- **Hand-off without a gap**: one process owns the store root at a time. On SIGTERM Lake
  hands each workspace store over, drains in-flight requests and releases the root, and a
  starting Lake opens the running workspaces' stores in the background.
- **Deployed by the operator** as a `Lake` custom resource, from a private image built on the
  cluster BuildKit, as a numeric non-root user. The operator provisions Postgres and applies
  the schema once; **Lake never runs schema migrations from its own pods.**
- **Configuration** is documented flag by flag in
  [`docs/serving/configuration.md`](../serving/configuration.md).

## Known issues

- **Security: #562** — `sign_in_sso` issues
  a session for an SSO identity it never verifies. An anonymous caller who knows an enabled
  provider's id and issuer and a provisioned user's external id receives that user's session.
  **Do not enable an SSO provider on an instance others can reach until this is fixed.**
- **#526** — a search history scan answers
  500 `invalid UTF-8` on a repository with a binary blob, and later scans in that space keep
  failing.
- **#524** — deleting an agent leaves its
  service launches, whose pods then crash-loop.
- **#560** — a drive upload fails into a
  repository with no `main` yet, or into a folder that does not exist.
- **#522** — a workspace store does not yet
  detect rollback, tail loss or resurrection; the signed manifest is not built.
- **#275** — `receive_agent_events` scans
  the whole agent-events topic, which grows without bound.
- **#287** — each Opportunities scan adds
  to the last one's, so near-duplicates pile up.
- **#636** — search titles code hits with
  raw workspace and repository ids.

## Running it

Lake is deployed by [`oramasearch/orama-operator`](https://github.com/oramasearch/orama-operator)
as a `Lake` custom resource, from an `oramasearch/lake:<tag>` image. The operator must vendor the
schema bytes of this tag before it serves this binary. See
[`docs/control-plane/schema.md`](../control-plane/schema.md).

To build and run locally, see [`docs/build/local.md`](../build/local.md). The build needs a
checkout of Zetta (`LAKE_ZETTA_SOURCE_DIR`) and of liquid (`LAKE_LIQUID_SOURCE_DIR`).
