# v0.1.0

**Released:** 2026-10-12 · **Branch:** `main` · **Previous:** none. This is the first tagged release.

Lake is the hosted service around liquid: one C++26 binary that serves a web app, a REST API
and an MCP server over the same registry of capabilities. A person signs in, gets workspaces,
and in each one designs, trains and ships: data, pipelines, models, agents, apps, repositories
and drives. Each workspace's data lives in that workspace's own Zetta; Lake's Postgres holds
only who the customers are and which Zetta serves which workspace.

This tag is the source the development deployment runs: `lake.oramadev.net` reports revision
`dd1574fd` from `GET /v1/server_info`, the commit this release is cut from apart from the
version string and this page.

619 commits across 177 pull requests since the first commit on 2026-09-02. The deployed
OpenAPI lists **554** `/v1` paths. The control-plane schema is at migration
`0083_methodology_deployments`.

> **Read [Known issues](#known-issues) before exposing an instance.** One of them is an open
> security defect in `sign_in_sso`.

## What `v0.1.0` includes

Each area below is implemented in the source tree. [`docs/design/status.md`](../design/status.md)
says, area by area, what has also been exercised locally and in the deployment. **A route in
the OpenAPI shows that a capability is deployed, not that it has been exercised end to end.**

### One registry, three surfaces

Every capability is registered once and answered over REST (`/v1/<capability>`), MCP (`/mcp`)
and the web app, which calls only `/v1`. A workspace-scoped client can use
`/w/<workspace_id>/v1/...` and `/w/<workspace_id>/mcp`. Errors come from one documented table
([`docs/api/errors.md`](../api/errors.md)).

### Accounts, sign-in and access

- Personal and organization accounts, memberships, teams, invitations and grants.
- Sign-in by Clerk in the browser, password, passkeys, OAuth providers, SSO (OIDC and SAML)
  and SCIM provisioning; MFA; sessions and devices that can be listed and revoked.
- Tokens and agent keys, including opt-in keys that never expire.
- An audit trail split by subject: control-plane and identity events in the central signed
  chain, events about a workspace's data in that workspace.

### Workspaces

- Many workspaces per account, each with its own Zetta, started and sized through the
  operator.
- **Workspace data lives in the workspace's Zetta**, as sealed records: Ask Orama
  conversations, opportunities, drives and share links, forge records, secrets and leases,
  application users, keys, settings and webhooks, agent task content, repository usage and
  the workspace's own audit. Migration `0070_drop_moved_tables` dropped the central copies.
- A workspace's repositories can move into its own encrypted liquid store in its Zetta
  (`move_workspace_store`: plan, copy, verify, switch), with its search index beside it.
- Deleting a workspace lists what goes first (`dry_run`) and asks for the typed name.

### Design

- **Ask Orama** is the home page: a conversation that can propose and, on confirmation, act.
- **Opportunities**: a scan of a workspace's data that proposes projects.
- **Solutions**: Orama's read-only catalogue beside a workspace's own, each startable as a
  project with an agent-proposed foundation, policy, holdout, actions and ROI readout.
- **Agents**: Orama's Agent Library, the Agent Factory, and agents a workspace defines.
- **Pipelines** and **methodologies**, including a workspace's own methodologies written in
  Python.

### Train

- **Data**: upload, datasets, storage (a volume per store, and drives over your own R2, S3,
  B2, GCS or Azure bucket), streams with topic and message CRUD, and indexes.
- **Experiments** with live metric charts, run comparison and confirmed promotion.
- **Models**: versions with held-out scores, bring-your-own ONNX, XGBoost and LightGBM
  models, and artifacts over 24 MiB moved in chunks.
- **Agents**: launches, schedules (with IANA time zones), turns, and agents started by a
  workspace stream.

### Ship

- **Models** published behind `predict`, including a workspace methodology's model.
- **Apps**: desired state, builds in the cluster, bindings, environment, logs, events, custom
  domains, and Lake-protected sign-in for an app's visitors.
- **Services**: managed Zetta and Postgres clusters, and a preview catalogue of Kafka,
  ClickHouse, TiDB, Cassandra and Valkey.
- **Application authentication**: user pools, hosted identity, JWTs and webhooks for the apps
  a customer builds.

### Repositories, drives and the registry

- Repositories with sync, change-based review, issues, releases, webhooks, branch protection,
  import from GitHub and export.
- Drives over a repository, workspace files or a store, with shortcuts, share links, version
  history and restore.
- A registry for images, packages and models over one deduplicated store.
- Search over history and inside artifacts.

### Secrets, keys and certificates

- Secret mounts with versions, dynamic-secret leases, encryption keys (encrypt, decrypt,
  sign, verify, rewrap, rotate), and a certificate authority (X.509 and SSH certificates,
  SVIDs).
- A user's secret reaches a Kubernetes Secret only as a sealed projection minted for the
  operator.
- A transparency log with checkpoints, proofs, TUF metadata and timestamp evidence.

### MCP connections

A workspace can be the client of remote MCP servers: the connection record and its secret,
OAuth sign-in, a read-or-change rule per tool with optional auto-approve, and re-export of
those tools through Lake's own MCP.

### Usage and billing

- Usage over time per workspace (API and MCP calls, model answers, compute as CPU, RAM, GPU
  and GPU memory, storage), with limits and CSV.
- Billing records in Postgres: plans, a price list, subscriptions, invoices and payments, with
  Stripe as the payment provider. Billing is off unless `LAKE_BILLING` is set; usage tracking
  is always on.

### The web app and the docs

The console is a web app embedded in the binary, with light and dark themes and a phone
layout. The customer guides are served at `/docs` from [`docs/guide/`](../guide/).

## What `v0.1.0` does **not** include

- **A production environment.** The only instance is the development deployment.
- **Automatic invoicing.** A month's invoices are issued by hand
  ([#621](https://github.com/oramasearch/lake/issues/621)), and not every kind of usage is
  metered yet ([#658](https://github.com/oramasearch/lake/issues/658)).
- **All state in workspace Zettas.** Apps, builds, stores, agent launches and schedules,
  identity, PKI and recovery tables are still in Postgres; each has its own open issue
  ([#315](https://github.com/oramasearch/lake/issues/315) to
  [#378](https://github.com/oramasearch/lake/issues/378)).
- **Every engine capability.** Zetta parity is tracked in
  [#185](https://github.com/oramasearch/lake/issues/185).
- **Storage phases 2 to 4** as designed
  ([#219](https://github.com/oramasearch/lake/issues/219),
  [#220](https://github.com/oramasearch/lake/issues/220),
  [#221](https://github.com/oramasearch/lake/issues/221)).
- **Pagination on every list page** ([#227](https://github.com/oramasearch/lake/issues/227)).
- **Native agents on the Orama base model**
  ([#246](https://github.com/oramasearch/lake/issues/246)).

## Known issues

- **Security: [#562](https://github.com/oramasearch/lake/issues/562)** — `sign_in_sso` issues
  a session for an SSO identity it never verifies. An anonymous caller who knows an enabled
  provider's id and issuer and a provisioned user's external id receives that user's session.
  **Do not enable an SSO provider on an instance others can reach until this is fixed.**
- **[#526](https://github.com/oramasearch/lake/issues/526)** — a search history scan answers
  500 `invalid UTF-8` on a repository with a binary blob, and later scans in that space keep
  failing.
- **[#524](https://github.com/oramasearch/lake/issues/524)** — deleting an agent leaves its
  service launches, whose pods then crash-loop.
- **[#560](https://github.com/oramasearch/lake/issues/560)** — a drive upload fails into a
  repository with no `main` yet, or into a folder that does not exist.
- **[#522](https://github.com/oramasearch/lake/issues/522)** — a workspace store does not yet
  detect rollback, tail loss or resurrection; the signed manifest is not built.
- **[#275](https://github.com/oramasearch/lake/issues/275)** — `receive_agent_events` scans
  the whole agent-events topic, which grows without bound.
- **[#287](https://github.com/oramasearch/lake/issues/287)** — each Opportunities scan adds
  to the last one's, so near-duplicates pile up.
- **[#636](https://github.com/oramasearch/lake/issues/636)** — search titles code hits with
  raw workspace and repository ids.
- **[#224](https://github.com/oramasearch/lake/issues/224)** — the walkthroughs leave their
  test datasets, indexes and services behind.
- **Tests that fail on a loaded host**:
  [#718](https://github.com/oramasearch/lake/issues/718) (a workspace store crash test
  segfaults under `ctest -j 6`) and
  [#618](https://github.com/oramasearch/lake/issues/618) (a session authentication cost
  test).
- The page says "lake" where the product is "Lake" in places
  ([#641](https://github.com/oramasearch/lake/issues/641)).

**Full suite, run serially** (`ctest --test-dir build`, no `-j`) on the release branch, with
`LAKE_TEST_DB_URI` set so the Postgres-backed cases run. macOS arm64, Homebrew Clang 22.1.8,
Homebrew PostgreSQL, liquid at `88c5ef4` and Zetta at `2cfdac21` (the sources the deployed

**The one failure was caused by this release and is fixed in it.**
`TelemetryHttp.MetricsRequireExistingAuthAndUsePrometheusContentType` repeated the version
`0.0.1` in the `lake_build_info` line it expected; it now reads `lake::version_string()`.
After the fix the test binary was rebuilt and the 25 tests of the telemetry, web app, server
info, OpenAPI and MCP groups were rerun: 25 of 25 passed. The other 997 were not rerun.

`./build/lake version` prints `lake 0.1.0`.

**Deployed:** `lake.oramadev.net` runs `oramasearch/lake:20261011u`, revision `dd1574fd`, with
the operator's schema applied (`schemaVersion sha256:323a2f944b68`) and the `Lake` resource
`Ready`. That image predates the version string, so it reports `0.0.1`. Its image build ran the
web app's tests: 293 tests, 292 passed, 1 skipped.

Not done for this release: the shared-library suite (`build-shared`), the Linux lane on the
cluster BuildKit, and any end-to-end exercise in the deployment beyond what
[`docs/design/status.md`](../design/status.md) already records.

## Running it

Lake is deployed by [`oramasearch/orama-operator`](https://github.com/oramasearch/orama-operator)
as a `Lake` custom resource, from a private `oramasearch/lake:<tag>` image built on the cluster
BuildKit. The operator provisions Postgres and applies the schema once; **Lake never runs
schema migrations from its own pods.** The operator must vendor the schema bytes of this tag
before it serves this binary. See [`docs/deployment/aks.md`](../deployment/aks.md) and
[`docs/control-plane/schema.md`](../control-plane/schema.md).

To build and run locally, see [`docs/build/local.md`](../build/local.md). The build needs a
checkout of Zetta (`LAKE_ZETTA_SOURCE_DIR`) and of liquid (`LAKE_LIQUID_SOURCE_DIR`).
